# ADR-002: Cơ chế Xác thực Phi trạng thái bằng JWT và Phân quyền theo vai trò (RBAC)

* **Mã quyết định (Decision ID):** `ADR-002`
* **Ngày quyết định (Date):** 24/11/2026
* **Người đề xuất (Author):** Nguyễn Phan Thế Vinh (Team Lead / PM · Backend / Tester)
* **Người phản biện (Reviewer):** Trần Hà Anh Quân (Fullstack Developer / Tech Lead)
* **Trạng thái (Status):** Accepted (Đã phê duyệt và áp dụng chính thức)
* **Liên kết yêu cầu (Traceability):** FR-F01-01, FR-F01-02, FR-F01-03, FR-F01-04, BR-10, NFR-03, NFR-04, AC-F01-01..04

## 1. Bối cảnh và Đặt vấn đề (Context)

UniLib được xây dựng theo mô hình tách rời giữa Client (Single Page Application viết bằng React/Vite) và API Server (RESTful API viết bằng Express.js). Hệ thống phục vụ 3 nhóm đối tượng người dùng với quyền hạn khác nhau theo quy định tại `BR-10`:
1. **Bạn đọc (Reader):** Tra cứu danh mục, xem chi tiết đầu sách, đặt trước sách, theo dõi lịch sử và trạng thái mượn trả của chính mình.
2. **Thủ thư (Librarian):** Quản lý biên mục sách, quản lý bản sao vật lý, thực hiện thủ tục mượn/trả/gia hạn tại quầy lưu thông, xử lý hàng đợi giữ chỗ.
3. **Quản trị viên (Administrator):** Quản lý tài khoản người dùng, phân bổ vai trò, kích hoạt hoặc vô hiệu hóa tài khoản (`FR-F01-04`).

Các yêu cầu phi chức năng và an toàn thông tin bắt buộc:
- `NFR-03` (Bảo mật thông tin xác thực): Mật khẩu phải được băm bảo mật bằng thuật toán mạnh (bcrypt salt ≥ 10); tuyệt đối không lưu hoặc truyền tải mật khẩu dạng rõ; không rò rỉ mã băm trong API response hoặc console log.
- `NFR-04` (Kiểm soát truy cập RBAC): Phải từ chối truy cập 401 khi chưa xác thực, và trả 403 Forbidden khi người dùng cố truy cập endpoint vượt quá quyền hạn của vai trò.
- `AC-F01-02`: Đăng nhập thất bại (sai mật khẩu hoặc không tồn tại tài khoản) phải trả thông điệp lỗi chung (`Invalid username or password`) để chống kỹ thuật dò quét tài khoản (Username Enumeration).
- `AC-F01-04`: Tài khoản bị vô hiệu hóa (`isActive === false`) phải bị từ chối đăng nhập với HTTP 403 và thông báo tài khoản bị tạm khóa, không phát hành phiên đăng nhập.

## 2. Quyết định Kiến trúc (Decision)

Nhóm T05 thống nhất triển khai:
1. **Cơ chế xác thực phi trạng thái (Stateless Authentication) dựa trên JSON Web Token (JWT - RFC 7519):**
   - Sử dụng thuật toán mã hóa đối xứng `HS256` với khóa bí mật `JWT_SECRET` (độ dài tối thiểu 32 ký tự ngẫu nhiên).
   - Payload của JWT được tối giản hóa, chỉ bao gồm:
     ```json
     {
       "sub": "user-uuid-v4",
       "role": "Reader" | "Librarian" | "Administrator",
       "iat": 1700000000,
       "exp": 1700604800
     }
     ```
   - Thời hạn hiệu lực mặc định là 7 ngày (`JWT_EXPIRES_IN=7d`) cho môi trường phát triển.
2. **Bảo mật mật khẩu với `bcryptjs`:**
   - Mật khẩu người dùng được băm với độ phức tạp `saltRounds = 10` trước khi lưu vào cột `password_hash` của bảng `users`.
   - Trường `passwordHash` bị loại bỏ triệt để (`select` loại trừ) trong mọi câu lệnh truy vấn dữ liệu trả về client.
3. **Bộ Middleware bảo vệ hai lớp:**
   - `authenticate` middleware: Kiểm tra header `Authorization: Bearer <token>`, giải mã chữ ký JWT. Để ngăn ngừa việc sử dụng token hợp lệ của tài khoản vừa bị vô hiệu hóa, middleware đối chiếu ID người dùng trong CSDL để đảm bảo `isActive === true`.
   - `authorize(...allowedRoles)` middleware factory: Chặn bắt các truy cập trái quyền, so khớp vai trò của người dùng với danh sách vai trò cho phép, ném mã lỗi HTTP 403 `FORBIDDEN` nếu không trùng khớp.
4. **Quy ước Đăng xuất (Client-side Logout):**
   - Do sử dụng JWT stateless, việc đăng xuất được thực hiện bằng cách client chủ động xóa token khỏi bộ nhớ trình duyệt (`localStorage` hoặc in-memory state).
   - Endpoint `POST /api/auth/logout` trả HTTP 200 kèm thông điệp hướng dẫn client xóa token, đảm bảo tính tiện dụng khi tích hợp.

## 3. Các Phương án Thay thế Đã Cân nhắc (Alternatives Considered)

| Tiêu chí so sánh | JWT Stateless (Được chọn) | Server-side Session (Cookie + Redis) | OAuth2 / OpenID Connect ngoài |
| :--- | :--- | :--- | :--- |
| **Mô hình trạng thái** | Stateless (Phi trạng thái) | Stateful (Lưu trữ trạng thái tập trung) | Federated Identity (Phụ thuộc bên thứ ba) |
| **Chi phí hạ tầng** | 0 USD (Không cần thêm server) | Cần cụm máy chủ Redis riêng biệt | Phức tạp, phụ thuộc nhà cung cấp ngoài |
| **Khả năng thu hồi phiên** | Thu hồi gián tiếp qua cờ `isActive` trong DB | Thu hồi tức thì bằng cách xóa session key | Phụ thuộc cơ chế revoke của IdP |
| **Độ phức tạp tích hợp** | Thấp, dễ test bằng curl và Supertest | Trung bình, phức tạp với CORS/Cookie | Rất cao, vượt quá phạm vi PA2 |
| **Lý do bác bỏ** | — | Tăng độ phức tạp hạ tầng và vi phạm ngân sách 0 USD | Vi phạm phạm vi đóng băng SRS PA2 (chỉ xác thực nội bộ trường) |

## 4. Hệ quả và Đánh giá Tác động (Consequences)

### Tác động tích cực (Positive Consequences)
- **Tối ưu hiệu năng và khả năng mở rộng:** API Server không phải lưu trữ session state trong RAM, cho phép scale ngang dễ dàng.
- **Bảo mật phân tầng chặt chẽ:** Tách bạch rõ ràng giữa lỗi chưa đăng nhập (401 UNAUTHENTICATED) và lỗi sai vai trò (403 FORBIDDEN), đáp ứng chuẩn xác tiêu chí nghiệm thu `AC-F01-01` đến `AC-F01-04`.
- **Dễ dàng kiểm thử tự động:** Các bài test Supertest có thể sinh JWT giả lập cho từng vai trò chỉ bằng hàm tiện ích mà không cần qua bước login thực tế.

### Hạn chế và Biện pháp Giảm thiểu (Trade-offs & Mitigations)
- **Rủi ro rò rỉ khóa bí mật `JWT_SECRET`:**
  - *Biện pháp giảm thiểu:* Nhóm tuyệt đối không commit giá trị thật của `JWT_SECRET` lên Git. Đã đưa `.env` vào `.gitignore` và chỉ lưu file mẫu `.env.example` với giá trị giả định.
- **Độ trễ khi thu hồi quyền của người dùng:**
  - *Biện pháp giảm thiểu:* Middleware `authenticate` luôn kiểm tra trạng thái `user.isActive` trong CSDL cho mỗi request bảo vệ, đảm bảo nếu Administrator vô hiệu hóa một tài khoản (`isActive = false`), phiên của tài khoản đó sẽ bị chặn ngay lập tức ở request tiếp theo.
