# ADR-003: Kiến trúc Layered Modular Monolith trên Express.js kết hợp Single Page Application (SPA)

* **Liên kết yêu cầu (Traceability):** F01–F07, UC-01..12, SCR-01..12, NFR-01, NFR-02, NFR-07, BR-01..10

## 1. Bối cảnh và Đặt vấn đề (Context)

Dự án UniLib có các ràng buộc thực thi đặc thù theo đồ án Kiến trúc Phần mềm:
- **Quy mô và nhân sự:** Nhóm gồm 4 thành viên (Vinh, Quân, Ánh, Nguyên), thời gian thực hiện giới hạn trong 5 tuần (W1–W5), ngân sách tài chính là 0.00 USD.
- **Phạm vi chức năng:** Đã đóng băng cố định theo SRS PA2 gồm 6 tính năng bắt buộc Must-have (F01–F06) và 1 tính năng Should-have (F07).
- **Mối liên kết chặt chẽ giữa các domain nghiệp vụ:** Quy trình trả sách (F05) tác động trực tiếp đến trạng thái bản sao (F03) và phải tự động kích hoạt gán sách cho bạn đọc đầu tiên trong hàng đợi giữ chỗ (F06) theo quy tắc FIFO `BR-07`. Tất cả các thao tác này bắt buộc phải chạy trong cùng một giao dịch CSDL cục bộ để chống mất mát dữ liệu hoặc deadlock.
- **Yêu cầu phân công lao động:** Cần một kiến trúc cho phép 4 thành viên phát triển song song trên các phần việc khác nhau (Giao diện React, API controllers, Domain logic, CSDL & Migration) mà hạn chế tối đa xung đột khi hợp nhất mã nguồn (merge conflicts).

## 2. Quyết định Kiến trúc (Decision)

Nhóm T05 thống nhất lựa chọn mô hình kiến trúc **Layered Modular Monolith (Nguyên khối phân tầng theo module)** cho Backend kết hợp với **Single Page Application (SPA)** cho Frontend:

```
+-------------------------------------------------------------------+
|               Frontend Client (React 18 + Vite SPA)               |
|            SCR-01..12 Views · React Router · Context Auth         |
+-------------------------------------------------------------------+
                                  │  HTTPS / RESTful JSON
                                  ▼
+-------------------------------------------------------------------+
|               Backend API (Node.js 22 LTS + Express.js)           |
|                                                                   |
|  [Presentation Layer]                                             |
|  Helmet · CORS · RequestId · Authenticate & Authorize · Routes    |
|                                                                   |
|  [Domain / Application Layer - 7 Modules]                         |
|  auth · users · books · copies · loans · reservations · dashboard |
|                                                                   |
|  [Data Access Layer]                                              |
|  Prisma Client ORM · Interactive Transactions · Row-level Locks   |
+-------------------------------------------------------------------+
                                  │  TCP Socket Probe / SQL
                                  ▼
+-------------------------------------------------------------------+
|               Persistence Layer (PostgreSQL 16 Engine)            |
|       users · book_titles · book_copies · loans · reservations    |
+-------------------------------------------------------------------+
```

1. **Phân rã 3 tầng chuẩn mực (Layered Architecture):**
   - **Tầng Giao diện HTTP (Routes & Controllers):** Tiếp nhận HTTP request, parse dữ liệu, chạy middleware xác thực/phân quyền, gọi hàm nghiệp vụ tương ứng và chuẩn hóa định dạng trả về `{ items, pagination }` hoặc `{ data }`.
   - **Tầng Nghiệp vụ Ứng dụng (Domain Services):** Đóng gói toàn bộ quy tắc nghiệp vụ `BR-01` đến `BR-10`. Tầng này hoàn toàn độc lập với giao thức HTTP (không phụ thuộc vào `req`, `res`), giúp việc viết Unit Tests trở nên cực kỳ đơn giản và tin cậy.
   - **Tầng Truy cập Dữ liệu (Prisma Data Access Layer):** Chịu trách nhiệm thực thi các câu truy vấn và giao dịch ACID trên PostgreSQL.
2. **Cấu trúc thư mục module hóa (Modular Monolith):**
   - Mã nguồn Backend được gom nhóm thành 7 thư mục module nghiệp vụ tại `src/server/src/modules/` tương ứng với F01–F07.
   - Mỗi module tự quản lý bộ ba file: `*.routes.js`, `*.controller.js`, `*.service.js`.
3. **Cơ chế xử lý lỗi tập trung (Error Envelope):**
   - Mọi lỗi trong hệ thống đều được dẫn xuất qua `AppError` hoặc `HttpError` và được xử lý bởi `errorHandler` middleware.
   - Định dạng lỗi trả về thống nhất theo chuẩn: `{ error: { code, message, details } }`.
   - Stack trace chỉ được ghi vào log server trong môi trường development/debug và **tuyệt đối không bao giờ rò rỉ ra response của client** (`NFR-08`).

## 3. Các Phương án Thay thế Đã Cân nhắc (Alternatives Considered)

| Tiêu chí so sánh | Layered Modular Monolith (Được chọn) | Microservices Architecture | Server-Side Rendering (Next.js) |
| :--- | :--- | :--- | :--- |
| **Độ phức tạp triển khai** | Rất thấp (1 tiến trình Node.js + 1 DB) | Rất cao (Nhiều containers, API gateway, service discovery) | Trung bình |
| **Giao dịch phân tán** | Không cần (Giao dịch ACID cục bộ) | Cực kỳ phức tạp (Phải dùng Saga hoặc 2PC) | Không cần |
| **Độ trễ liên module** | In-process calls (Microseconds) | Network RPC / HTTP (Milliseconds) | In-process calls |
| **Phù hợp nhóm 4 người** | Tối ưu, dễ phân chia và kiểm thử | Quá tải, tốn công dựng hạ tầng | Hạn chế trong phân tách chuyên môn Frontend/Backend |
| **Lý do bác bỏ** | — | Bác bỏ vì độ phức tạp vượt quá thời gian W1-W5 và ngân sách $0 | Bác bỏ vì gây khó khăn cho việc viết test Supertest độc lập cho REST API |

## 4. Hệ quả và Đánh giá Tác động (Consequences)

### Tác động tích cực (Positive Consequences)
- **Đơn giản hóa hạ tầng và tối ưu chi phí:** Toàn bộ hệ thống Backend chạy trong một container/process duy nhất, dễ dàng deploy lên môi trường miễn phí như Render.
- **Toàn vẹn lưu thông sách:** Các tác vụ phức tạp (như trả sách và chuyển trạng thái bản sao sang `Reserved` cho bạn đọc kế tiếp trong hàng đợi) được thực thi trong một `prisma.$transaction` duy nhất, không lo lắng về lỗi đồng bộ mạng giữa các dịch vụ.
- **Tốc độ thực thi kiểm thử:** Toàn bộ bộ test Jest 8 test suites chạy hoàn tất chỉ trong 2-5 giây, hỗ trợ tối đa quy trình tích hợp liên tục (CI).

### Hạn chế và Biện pháp Giảm thiểu (Trade-offs & Mitigations)
- **Rủi ro ranh giới module bị phá vỡ (Tight Coupling):** Lập trình viên có thể vô tình gọi chéo trực tiếp database table của module khác thay vì thông qua Service công khai.
  - *Biện pháp giảm thiểu:* Nhóm thiết lập quy tắc Review chéo (`copilot-instructions.md` và PR template) bắt buộc kiểm tra xem service của module có tuân thủ đúng hợp đồng giao tiếp được định nghĩa tại `docs/design/api.md` hay không.
- **Rủi ro sập toàn bộ ứng dụng khi 1 module lỗi nặng:**
  - *Biện pháp giảm thiểu:* Middleware bắt lỗi tập trung `errorHandler` bọc ngoài toàn bộ luồng xử lý và socket probe `checkDatabaseHealth` đảm bảo server không bao giờ bị crash đột ngột ngay cả khi mất kết nối CSDL tạm thời.
