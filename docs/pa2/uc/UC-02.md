# UC-02 — Manage User Accounts

**Feature:** F01 (Must) | **Primary actor:** Administrator | **Screen:** SCR-02
**Linked requirements:** FR-F01-04, FR-F01-02, BR-10, NFR-03, NFR-04
**Task:** PA2-Q5 | **Owner:** Tran Ha Anh Quan | **Reviewer:** Vinh / Nguyen
**Status:** Ready for peer review | **Registry:** v1.0.0-frozen

## Goal and scope

An authorized Administrator creates a user account, assigns its Reader/Librarian/Administrator role, or changes an existing account's role or active status. This use case does not introduce public self-registration, account recovery or additional role types.

## Trigger, preconditions and guarantees

- **Trigger:** Administrator opens the user-management function.
- **Preconditions:** Valid Administrator session; endpoint passes JWT and RBAC checks (UC-01, NFR-04).
- **Success postconditions:** New or edited account and authorized role/status changes are persisted, and the user list displays the current values. Credentials are hashed as specified by NFR-03.
- **Failure guarantee:** Invalid, unauthorized or duplicate requests make no partial user/role changes.

## Main success scenario — Create an account

1. The Administrator opens SCR-02 and selects **Create User**.
2. UniLib displays required account fields and an allowed-role selector.
3. The Administrator enters account identity, initial credentials and selects one frozen role.
4. UniLib validates required fields, identifier uniqueness and the selected role.
5. UniLib hashes the password using bcrypt with cost at least 10.
6. UniLib persists the user account with the selected role and the chosen active status.
7. UniLib confirms account creation and refreshes the user list without returning credentials or hashes.

## Alternate and exception flows

- **A1 — Change role:** At step 1 the Administrator selects an existing account, chooses a different allowed role and confirms. UniLib validates Administrator rights, saves the role and refreshes SCR-02.
- **A2 — Activate/deactivate:** The Administrator selects an existing account and changes Active/Inactive. UniLib persists the change; future protected actions for an inactive account must be governed by the agreed security policy (see open decision).
- **E1 — Missing/invalid fields:** At step 4, reject input with field-level guidance; no account is saved.
- **E2 — Duplicate username/email:** At step 4, display a uniqueness error; preserve input for correction.
- **E3 — Permission failure:** Missing/invalid JWT returns 401; a non-Administrator caller returns 403. Do not expose user lists.
- **E4 — Persistence failure:** Roll back the change and show a user-safe error.

## Data and business invariants

An account has one of the frozen roles: Reader, Librarian or Administrator. Account identity fields must be unique under the approved schema. NFR-03 governs password persistence; BR-10 and NFR-04 govern access. Changes to roles are authoritative server-side, not client-side. The effect of deactivating a logged-in user and whether to prevent deactivation of the last Administrator require policy confirmation.
